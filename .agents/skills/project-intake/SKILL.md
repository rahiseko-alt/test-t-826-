# Project Intake Skill (最初の受け口)

依頼文がまだどこにも無い状態で、**1案件につき1回だけ**「何を作るか」を利用者から受け取る手順です。
受け取ったら、追加で聞かずに [`project-spec` スキル](../project-spec/SKILL.md) 手順1へ渡します。

> **なぜ独立した手順か**: [`session-checkin`](../session-checkin/SKILL.md) は「前セッションの続きを続ける」手順であり、続きが無い最初の1回を持ちません。
> `project-spec` は「依頼文から読み取れる内容で埋める」手順であり、依頼文そのものを受け取る場面を持ちません。
> その隙間の1回だけがここです。**ここに入る回数が案件数を超えたら、この手順は失敗しています**（AGENTS.md 避けるべき未来3位）。

## 起動条件 (Triggers)

次の3つが**すべて**成り立つときだけ起動します。1つでも欠けたら起動せず `project-spec` 手順1から始めます。

1. `spec.md` 第1節・第2節の記入欄が空である。
2. git 履歴・`docs/handoff.md` に依頼の内容が無い。
3. 現在の会話にも依頼文が無い。

## 手順 (Workflow)

1. **現在地を1〜2行で述べる。** 長い状態報告を先に書かない。利用者が最初に読むのは尋ねられている内容であるべきです。
2. **下の文言で1回だけ尋ねる。**
3. **返答が来たら、そのまま `project-spec` 手順1へ渡す。** 短くても曖昧でも聞き返しません。読み取れない箇所は最も確からしい案で埋め、門①の二択に判定させます。

## 文言 (Wording)

> 案件名・語尾は案件に合わせて調整してよいが、**次の4つの要素と順序は変えない**——
> ①一度きりだと最初に言う ②尋ねるのは1つだけ ③答えなくてよいものを明示する ④この後の流れと確認の終わりを1行で示す。

```text
この案件で最初の1回だけ、うかがいます。（毎回ではありません。次のセッションからは、この質問は出ません。）

このリポジトリはまだ雛形の状態で、何を作る案件かがどこにも書かれていません。ここを私の想像で埋めると、
実在しない目標に向かって以降の判断が全部そこを見に行くことになるため、ここだけお聞きします。

**今回作るものは何ですか。** 誰が使って、その人の何が楽になるのかを、普段の言葉で数行いただければ十分です。

- 決めていただかなくてよいもの: 画面の作り・使う技術・作る順番。こちらで決めます。
- きれいに書けなくても大丈夫です。足りないところは、こちらで最も確からしい案を埋めます。

このあと、いただいた文から案をまとめ、別のAIに「これは結局、何が実現するのか」を1文に戻させて
**「そう／違う」の二択**でお見せします。**確認はその1回で終わりです。**
```

### なぜこの順序か

- **「一度きり」を最初に置く理由**: 後ろに置くと、利用者は読み終える前に「毎セッションこれをやるのか」と判断します。実際にその問い返しが発生しました（`docs/failures.md` F-20260826-01）。
- **「答えなくてよいもの」を書く理由**: 書かないと、利用者は画面や技術まで答えようとして手が止まります。手間を案件数に比例させないための一文です（AGENTS.md 避けるべき未来3位）。
- **最後に確認の終わりを宣言する理由**: 「二択が最後」と言い切らない限り、利用者から見て確認の回数は未知のまま残ります。

## 禁止事項 (Do Not)

- **2回以上尋ねない。** ヒアリング・追加質問・案の複数提示はいずれもこれに該当します。
- **尋ねる前に長い状態報告を書かない。** 現在地は1〜2行で足ります。
- **選択肢を並べて選ばせない。技術用語で範囲を指定させない**（AGENTS.md D-2、`docs/handoff.md` 禁止事項2〜3）。
- **起動条件を1つでも欠く場面で起動しない。** 会話に依頼文がある時点で、この手順は不要です。
- **門①をここで回さない。** 回すのは `project-spec` 手順2です。
