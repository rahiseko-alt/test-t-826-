# Verified Plan Skill (検証済み計画プロトコル)

計画を立て、**別の目で反証させ**、全件を処理し、合格基準を先に決めてから実装する手順。

## 発火条件 (When)

- **STRICT と判定された変更**（`AGENTS.md` LEVEL C 第1節の判定キーワード: auth / payment / personal data / public release / production DB / migration）
- または**ユーザーが計画を求めたとき**

**FAST の変更には使わない。** 複数ファイルに触るというだけでは発火しない（LEVEL C 第1節は複数ファイル変更を FAST に分類している）。毎タスクに適用すれば儀式になり、確認と工程だけが増える。

## 手順 (Workflow)

1. **計画ドラフト** — 次の見出しを必ず含める。`## 対象明細`（解消・実現する項目を**1件ずつ列挙**する。番号だけの参照は禁止。「全部やった」を後から反証可能にするため）／`## 反証の採否`／`## 受け入れ条件`／Context／フェーズ／DoD（6項目以内）。並列で実行する場合のみ、担当割りと**パス契約**（参照パスの固定・記録番号の事前割当・部分失敗時の詰め方）を書く。
2. **敵対検証** — [`plan-refuter`](../../../prompts/plan-refuter.md) と [`acceptance-designer`](../../../prompts/acceptance-designer.md) を**並列・フレッシュコンテキスト**で実行する。計画を書いた本人に検証させない。渡すときは、計画の主張を**照合先リスト**（実測すべきファイル名と数値）に展開して渡す。「計画を読め」だけでは前提の受け売りが返る。**両者の生出力はファイルに保存する**（後から採否の突合ができる）。
3. **修正ループ** — 全反証を「**採用**（計画を修正）／**却下**（理由を計画に記録）／**限界**（残項目として記録）」の3分類で処理し、`## 反証の採否` に全件残す。**「高」が出た周は、修正後に refuter へ1回差し戻す。** 成果物や対象明細が変わったときは designer にも差し戻す（古い計画を検収する条件を残さないため）。差し戻しは **refuter・designer 各々最大2周**。**打ち切りが優先**——残った「高」や未再設計の条件は握りつぶさず限界として記録する。
4. **承認（ユーザーが計画を求めた場合のみ）** — 発火条件だけで動いた場合は承認を求めず実装に進み、計画は記録として残す。手が止まっていないのに確認を投げない。承認を求めるときは、**計画を書いていない別エージェントに計画本文だけを渡し**「これは結局何をしようとしているのか」を1文で書かせ、冒頭に掲示する（判断材料。ユーザーに詳細を読ませないため）。
5. **実装規律** — 計画のパス契約と受け入れ条件が正。**計画外の変更を行わない**（必要が生じたら先に計画を改訂して記録する）。受け入れ条件のいずれかが達成不能と判明した時点で実装を止め、計画を改訂する（計画どおりに完走して無意味になることを防ぐ）。受け入れ条件が全部クリアするまで**完了と言わない**。計画が終わるまで**次の課題に着手しない**。完了時に門②（`AGENTS.md` 冒頭）。

## 禁止事項 (Do Not)

- 計画を書いた本人に反証・受け入れ条件設計をさせない。自己検証は機能しない。
- 反証を握りつぶさない。却下は正当だが、記録しない却下は許されない（検知の原則5）。
- 受け入れ条件に「ファイルを作成した」だけの条件を置かない。動作・整合で書く。
- 手順4の1文要約を門①と呼ばない。**門①は案件のゴールを決めるとき1回だけ回すものであり、入力は `spec.md`**（AGENTS.md D-1）。計画ごとに門①を回してはならない。
