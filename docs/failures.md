# 失敗記録 (docs/failures.md)

> **運用ルール**
> - **追記のみ (Append-Only)。** 過去の記録を書き換えない。
> - **全文を読み込まない。** 照合が必要なときだけ `failure-matcher`（[`prompts/failure-matcher.md`](../prompts/failure-matcher.md)）が参照する。
> - 作業中に発生し**解決した**失敗を、下の形式で末尾に追記する。

## 形式

```text
### [F-YYYYMMDD-NN] 1行で言うと何が起きたか

- **Date**: YYYY-MM-DD
- **Category**: (例: process / build / test / deploy / communication)
- **Trigger/Context**: どういう場面で起きたか
- **Failure**: 実際に何が起きたか（事実のみ）
- **Root Cause**: なぜ起きたか（症状ではなく原因）
- **Guardrail / Prevention**: 次に同じ場面で何をすれば防げるか
```

### [F-20260826-01] 初回の質問が「毎回聞かれるのか」と受け取られ、利用者に1往復を追加させた

- **Date**: 2026-08-26
- **Category**: communication
- **Trigger/Context**: 雛形のままのリポジトリでセッションを開始し、`spec.md` が空だったため「今回作るものは何ですか」と尋ねた場面。
- **Failure**: 長い状態報告のあとに質問を置き、その質問が1案件に1回だけのものである旨をどこにも書かなかった。利用者から「これは初回セットアップのみの話か」という確認が返り、本題への回答の前に1往復を消費した。
- **Root Cause**: 頻度の宣言が文言に無かったこと。利用者から見て、確認が今後何回来るのかが未知のまま残っていた。回数が未知の確認は、利用者側に「回数を確かめる確認」を発生させる。
- **Guardrail / Prevention**: 依頼文が無い状態で尋ねるときは [`project-intake` スキル](../.agents/skills/project-intake/SKILL.md) の文言を使う。1行目で「この案件で最初の1回だけ」と述べ、末尾で「確認はその1回で終わり」と述べる。状態報告は1〜2行に抑え、質問より前に長文を置かない。

### [F-20260826-02] 二択の答え方を毎回言い換えており、利用者に「何と答えるか」を考えさせていた

- **Date**: 2026-08-26
- **Category**: communication
- **Trigger/Context**: 方針の確定を利用者に求める場面。
- **Failure**: 「そう／違う」「一言ください」など、二択の答え方をその場ごとに言い換えていた。利用者から、Yes/No で求めるよう指示が入った。
- **Root Cause**: 答え方の書式が決まっていなかったこと。二択そのものは設計に入っていたが、**どう答えさせるか**が各所の文面任せになっていた。書式が毎回変わると、利用者は中身の判断の前に「何と答えればよいか」の判断を1つ余計に行うことになる。
- **Guardrail / Prevention**: 二者択一は必ず「〜でよろしいですか？」と「Yes/No」の2行で終える（AGENTS.md D-2）。Gate 1の提示書式は [`prompts/intent-backtranslator.md`](../prompts/intent-backtranslator.md) が正であり、各スキルに複製しない。

### [F-20260826-03] 配り方だけを詰め、届いたものが何をするかを spec に一度も書かないままGate 1に出した

- **Date**: 2026-08-26
- **Category**: process
- **Trigger/Context**: 案件のゴールを `spec.md` に固定し、Gate 1（逆翻訳）にかけた場面。
- **Failure**: 戻ってきた1文が「たぶん、まだ実現する内容は決まっていません」だった。`spec.md` は、配布物の形・自動ダウンロード・ハッシュ照合・上書き禁止といった**手段**を精密に書いていた一方、届いた一式が利用者の何をどう変えるのかを1行も書いていなかった。第2節の検収条件4件がすべて「配る側の挙動」であり、この製品の価値を1件も捕まえていなかった。
- **Root Cause**: 利用者との対話が配り方（フォルダかmdか、DLか書き出しか、gitを使うか）に集中し、その流れのまま spec を書いたこと。個々の判断はどれも妥当だったが、**判断の対象が全部「手段」の側にあった**。AGENTS.md 避けるべき未来1位（仕組みづくりが目的化し、開発そのものが止まる）そのものであり、自覚できないという性質どおり、Gate 1に当たるまで気づかなかった。
- **Guardrail / Prevention**: 第2節を A群（届いたものが効いているか）と B群（正しく届くか）に分け、**B群が全部緑でも A群が1件でも赤なら検収は通らない**と明記した。検収条件を書き終えたら、「この条件が全部通ったとき、利用者の何が変わっているか」を1文で言えるか自問する。言えなければ手段しか書いていない。

### [F-20260827-01] 形式の縛りに合わせることに執着し、同じ確認を何度も繰り返させた

- **Date**: 2026-08-27
- **Category**: communication
- **Trigger/Context**: Gate 1 で spec のゴールを利用者に確認していた場面。
- **Failure**: 「1文にする」という形式の縛りを守ることに集中し、spec が7項目になった後もその縛りを維持した。結果として毎回1項目しか拾えない文が返り、利用者に同じ判定を何度もさせた。さらにその状況の説明として、縛りと文書の形が合っていない旨を長く述べ、利用者から「細かい事への執着の代表例」と指摘された。
- **Root Cause**: 判断の基準を「決めた形式に合っているか」に置いていたこと。本来の基準は「相手が読んで分かるか」であり、形式はその手段にすぎない。手段が目的に転化していた。
- **Guardrail / Prevention**: AGENTS.md D-2 に最優先ルールとして追加した。発言前に「この書き方は相手が読んで分かるか」「AIの都合で書いていないか」を必ず自問する。長さも形式も問わない。あわせて「1文で」「3行で」といった縛りを本文から外した（Gate 1 のプロンプト、spec.md A-4、docs/handoff.md）。

### [F-20260827-02] 完了を報告したまま黙って止まり、利用者を「壊れたのか」と困惑させた

- **Date**: 2026-08-27
- **Category**: communication
- **Trigger/Context**: 公開が完了し、その結果を報告した場面。
- **Failure**: 「出荷完了です」と述べたあと、次に何が起きるのか、利用者が次に何をすればよいのかを一切示さずに応答を終えた。利用者からは、全部終わったのか、途中で固まったのか、返事を待たれているのかが判別できず、「壊れたのかと困惑している」との指摘を受けた。
- **Root Cause**: 報告を「情報を伝えること」だと捉え、「相手が次に動けるようにすること」だと捉えていなかった。こちらは処理を終えて静止しているだけだが、**利用者から見れば、動いているのか死んでいるのかの区別がつかない。**
- **Guardrail / Prevention**: AGENTS.md D-2 に最優先ルールとして追加した。どの返答も、最後に「次に何が起きるのか」または「次に何をすればよいのか」を1行置く。全部終わったなら言い切ったうえで次にできることを示す。spec.md 第1節8番と A-7 が、この振る舞いを一式側にも要求する。

### [F-20260827-03] 指示書に「空のフォルダで始める」が無く、既存プロジェクトの中で衝突した

- **Date**: 2026-08-27
- **Category**: process
- **Trigger/Context**: 出荷した指示書を、利用者が実際にAIへ渡した最初の1回。
- **Failure**: 既存のファイルがあるフォルダで実行され、`AGENTS.md` / `CLAUDE.md` / `docs/*.md` の5件と衝突した。停止の仕組みは正しく働き（A-8 と B-3 が実地で通った）既存ファイルは1つも変わらなかったが、**利用者は最初の1回目でいきなり判断を求められた。**
- **Root Cause**: 指示書が「どこで作業するか」を一度も述べていなかった。上書きを止める仕組みは用意したが、**そもそも衝突が起きない場所で始めさせる**という、より手前の手当てが抜けていた。停止は最後の砦であって、最初の設計ではない。
- **Guardrail / Prevention**: 指示書の先頭に手順0「新しい空のフォルダを作り、その中で作業する」を追加した。すでに何か入っているフォルダで始めてしまった場合は、既存ファイルに触れず、やり直してよいかを利用者に確認させる。画面の案内文にも同じ一言を入れた。E2E（B-1）に、この指示が指示書へ入っていることの確認を追加した。

### [F-20260827-04] 置けたか確かめる手順が実地で飛ばされ、確認なしに実装へ進みかけた

- **Date**: 2026-08-27
- **Category**: process
- **Trigger/Context**: 出荷した指示書を実際にAIへ渡し、一式の展開まで進んだ場面。
- **Failure**: 手順4（`scripts/verify-install.sh`）が一度も実行されず、出力も出ないまま `spec.md` の記入へ進んだ。一式が本当に揃っているかを誰も確かめていない状態で、以降の作業が始まりかけた。
- **Root Cause**: 2つある。第一に、指示書がカレントディレクトリを前提に `bash scripts/verify-install.sh` とだけ書いており、別のフォルダへ展開した場合にパスが合わなかった。第二に、その手順を飛ばしてはならないと明示していなかった。**強制力の無い手順は飛ばされる。** 検査は「置いてある」だけでは効かず、「飛ばせない」ようにして初めて効く。
- **Guardrail / Prevention**: 手順4の見出しを「飛ばしてはいけません」に変え、`cd <展開したフォルダ>` を明示した。「問題なし」が出るまで spec.md の記入にも実装にも進むな、と書いた。手順5として、結果を1行で利用者へ伝えることを追加した。E2E（B-1）に、指示書へ `verify-install.sh` と「飛ばして」が入っていることの確認を足した。
- **あわせて**: この修正中に `index.html` の JavaScript を壊した（文字列の閉じ忘れ）。E2E の①が即座に落ちて捕まえた。検査が歯を持っていることの実地確認になった。

### [F-20260827-05] 同じ選択肢を何度も再掲し、自分の操作の反響まで毎回報告した

- **Date**: 2026-08-27
- **Category**: communication
- **Trigger/Context**: 利用者の返事を待っている間に、自分が出したPRのマージ通知が届いた場面。
- **Failure**: 通知を処理するたびに「私の操作の反響で、対応は不要です」と述べ、さらに前回出した選択肢をそのまま再掲した。これを何度も繰り返し、利用者から「さっきから同じ内容が何回も表示される。修正しろ」と指摘を受けた。
- **Root Cause**: 2つある。第一に、「黙って止まらない」ルールを満たそうとして、待機中であることを伝えるたびに選択肢ごと再掲した。**待っていることを伝えるのに、選択肢の再掲は要らない。**第二に、自分の操作の通知を「起きたこと」として報告していた。**自分が起こした変化は、利用者にとって新しい事実を1つも含まない。**
- **Guardrail / Prevention**: AGENTS.md D-2 に2つ追加した。同じ内容を二度出さない（待機中なら1行）。自分の操作の反響を報告しない（黙って処理する）。

### [F-20260827-06] 繰り返しを禁じたルール自身が繰り返しを生んだ（適用範囲の未定義）

- **Date**: 2026-08-27
- **Category**: communication
- **Trigger/Context**: F-20260827-05 で「同じ内容を二度出さない」を追加した直後。
- **Failure**: 追加した直後の応答で、「前回の選択肢のまま待っています」を2ターン連続で表示した。利用者が何も送っていないターン（通知の処理だけのターン）でも発言していたためである。直したと述べた直後に同じ症状を再現した。
- **Root Cause**: **ルールの適用範囲を決めていなかった。** 「報告して終わらない（どの返答も最後に次を示す）」の「どの返答も」に、利用者が発言していないターンまで含めてしまった。そのルールは利用者の発言に対する返答のためのものであり、通知処理のターンに適用すると、毎回「待っています」を出力することになる。**繰り返しを禁じるルールを足したのに、既存ルールの適用範囲が広すぎたせいで、繰り返しが構造的に発生し続けた。**
- **Guardrail / Prevention**: AGENTS.md D-2 に、利用者が何も言っていないターンでは何も表示しない、を追加した。「報告して終わらない」は利用者の発言に対する返答にだけ適用する、と適用範囲を明記した。**新しいルールを足すときは、既存ルールとの適用範囲の重なりを必ず確かめる。**


## F-20260827-07 — 検査の1行目が判定でなかった

**症状**: 配布中の一式で `scripts/verify-install.sh` を実行すると、1行目が
`--- 開発のしたく / 置けたかの確認 ---` という見出しだった。指示書は
「出力の1行目をそのまま利用者に見せてください」と書いているため、
コードを読めない人が最初に見る行が、判定ではなく飾りになっていた。

**なぜ見つからなかったか**: スクリプト冒頭のコメントには
「1行目に『問題なし』か『要対応』を必ず出す」と書いてあった。書いた本人が
書いたつもりになり、実際の出力を1行だけ見る確認をしていなかった。
E2E（B群）は届き方しか見ないため、ここは通り抜ける。

**直し方**: 見出しと対象パスを判定より後ろへ移した。判定行の直前に
「ここへ何かを足さないこと」と理由つきで書き添えた。

**証拠**: 赤（直す前の1行目が見出し）→ 緑（直した後は「問題なし」）
→ 戻して赤（欠けを作ると「要対応」）を実機で確認。

## F-20260827-09 — 「手間が減る」と書いたせいで、それ以外の要望が言えなくなっていた

**症状**: 画面の呼びかけが「誰が使って、その人のどんな手間が減るとうれしいか」だった。
添えた例も2つとも手間を減らす話（予約の電話・売上の集計）だった。
利用者から「手間が減る事じゃない要望に対応していないのか？」と指摘を受けた。

**実際はどうか**: 一式の側には何の制限も無い。`spec.md` 第1節はもともと
「誰の**何が良くなるか**」であり、動機を問わない。狭めていたのは呼びかけの文言だけ。

**なぜ起きたか**: 例を「粒度の見本」としか捉えていなかった。実際には、例は
**「何を頼んでよいか」の範囲宣言としても読まれる**。同じ動機の例を2つ並べた時点で、
売上を増やしたい・作ったものを見てもらいたい・間違いを無くしたい、といった要望は
「ここで言うものではない」と受け取られ、黙って落ちる。落ちたことは誰にも見えない。

**直し方**: 呼びかけを `spec.md` 第1節と同じ「何が良くなるか」に戻し、
「減らしたいことでも、増やしたいことでも、今まで無かったものでもかまいません」を添えた。
例を3つにし、動機を **減らす / 見てもらう / 間違いを無くす** に散らした。
`project-intake` スキルの「書くときの5点」3番にも、動機を散らす理由として書き足した。

**教訓**: 呼びかけと例は、対応範囲そのものである。文言で狭めた範囲は、
機能で広げても届かない。

## F-20260827-10 — 「上書きしてはいけません」と書いただけで、実際は黙って上書きしていた

**症状**: 指示書の手順3は `tar -xzf shitaku-kit.tar.gz` の1行だけで、その下に
「同じ名前のファイルやフォルダが既にある場合、上書きしてはいけません」と
書いてあった。既存の `AGENTS.md` と `docs/handoff.md` を置いたフォルダで
この1行を実行したところ、**終了コード0のまま、両方とも一式の中身に置き換わった。**
利用者の書いたものは消え、画面にも何も出なかった。

**なぜ起きたか**: 上書きしないことの担保を、AIが文を読んで守ることに委ねていた。
`spec.md` 第3節は「正しく置かれたかの判定を、AIの判断に委ねない」と書いており、
第4節はデータの上書きを停止4領域として挙げている。にもかかわらず、手順3だけが
文による禁止で終わっていた。**禁止の文は、実行される1行に勝てない。**

**なぜ検査を通り抜けたか**: B群（E2E）は指示書に「上書き」という語が入っているかを
見ていた。語は入っていた。中身が効いているかは見ていなかった。

**直し方**: 手順3を、展開の前に同じ名前のものを調べ、1つでもあれば
`要対応` を出して**何も書かずに終わる**ブロックへ差し替えた。調べる名前の一覧は
`scripts/build-kit.sh` が現物の一式から拾って `index.html` へ埋める（手で書くと、
一式に足したものが一覧から漏れ、そのファイルだけ黙って上書きされる）。
E2E 側も「語があるか」から「そのブロックがあるか」へ変えた。

**証拠**: 赤（素の `tar -xzf` が既存2ファイルを exit 0 のまま置き換える）→
緑（新しいブロックは `要対応` を出し、フォルダの中身が1バイトも変わらない。
空のフォルダでは `問題なし` を出して展開し、`verify-install.sh` まで通る）→
戻して赤（手順3を素の1行に戻すと E2E ① が落ち、実機でも同じ上書きが再現する）。

**教訓**: 停止4領域（金額・日付・権限・削除／上書き）に文で禁止を書いたら、
**その禁止が機械で効いているかを、実際に壊しにいって確かめる。** 語の有無を見る
検査は、語があるだけの状態を緑にする。
