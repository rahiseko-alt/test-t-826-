# 受入検査（E2E）の雛形と、その転写手順

このディレクトリの [`acceptance.spec.ts`](./acceptance.spec.ts) は、案件ごとに書き換えて使う
Playwright の雛形です。設計の正は
過去の判断
の第4節です。

案件側の仕様は `spec.md` に書きます。その雛形は
[`docs/templates/project-spec.md`](../../spec.md) にあります。
**この雛形が入力に取るのは、その第2節（検収条件）と第4節（保護対象ルート一覧）の2つです。**

---

## 1. 何を、何回、どの順で確かめるか

1回のブラウザ起動に6段を束ねます。ブラウザの起動が費用の大半を占めるため、
同じ session の中で入力値を変えて試す分はほとんど無料になります。

| 順 | 内容 | 落ちたとき | 入力元 |
|---|---|---|---|
| ① | ハッピーパス1周 | **即終了。以降を走らせない** | spec.md 第2節 |
| ② | 画面への引っ掛け（代表数件） | 記録して続行 | 機械生成 |
| ③ | API層への引っ掛け（数百件・ブラウザを通さない） | 記録して続行 | 機械生成 |
| ④ | 2周目（状態が残っていないか） | 記録 | ①と同じ手順 |
| ⑤ | 権限（未ログイン／他人として到達できないか） | 記録 | spec.md 第4節 |
| ⑥ | 記録の集計 | ②〜⑤で1件でも記録があれば落とす | — |

①だけが即時終了です。`test.describe.serial` は前のテストが落ちると以降を走らせないため、
①が投げれば②以降は実行されません。②〜⑤はその場では投げず、`findings` に積んで
⑥でまとめて落とします。

**①を先頭に置くのは切り分けのためです。** ハッピーパスが壊れていると
引っ掛けも全部落ち、落ちる理由が全部「画面に到達できなかった」になります。

## 2. spec.md 第2節を、どこにどう転写するか

`acceptance.spec.ts` の中には `[転写N]` という形のマーカーコメントが置いてあります。
書き換えるのはマーカーで挟まれた中だけです。それ以外は触りません。

| マーカー | 転写元 | 何を書くか |
|---|---|---|
| `[転写1]` | spec.md 第2節の **Given** | 前提の準備。ログイン、初期データの用意 |
| `[転写2]` | spec.md 第2節の **When** | URL到達から最終出力までの通し操作 |
| `[転写3]` | spec.md 第2節の **Then** | 期待される最終出力の確認 |
| `[転写4]` | 第2節の When と同じ経路 | ②で引っ掛け値を入れる入力欄と送信ボタン |
| `[転写5]` | 第2節の When に対応する API | ③が叩く入口。ブラウザを通さない |
| `[転写6]` | 案件のログイン画面 | ⑤「他人として」で使う別人のログイン手順 |

各マーカーには `[転写N ここまで]` が対応しています。

### 手順

1. `templates/e2e/acceptance.spec.ts` を案件リポジトリの `e2e/acceptance.spec.ts` に複写する。
2. spec.md 第2節の Given-When-Then を上から順に読み、`[転写1]`〜`[転写3]` の中に
   **1手順1文で、順番を変えずに**置き換える。
   セレクタは `getByRole` / `getByLabel` を使い、CSS クラス名には依存させない。
3. `[転写4]` に、②で使う入力欄と送信ボタンを書く。①の When と同じ経路にする。
   別経路にすると、①が通って②が落ちたときに原因が2つに増える。
4. `[転写5]` に、③が叩く API の入口を書く。ここはブラウザを通しません。
   `page` ではなく `api`（Playwright の `request`）を使います。
5. `[転写6]` に、別人としてのログイン手順を書く。
   環境変数 `OTHER_LOGIN_ID` / `OTHER_LOGIN_PW` を設定しない場合、⑤は
   「他人としての到達を検査していない」を記録して落ちます。黙って緑にはなりません。
6. ④は①の When と Then の再掲です。①を書き換えたら④も同じに直す。

### 手順の数を減らさないこと

spec.md 第2節の手順を減らすと、
[`scripts/check-test-integrity.sh`](../../scripts/check-test-integrity.sh) の T5 が
Given / When / Then の行数の減少として検出します。
逆に、**spec.md を残したまま `acceptance.spec.ts` 側だけを短くした場合は検出されません。**
手順の数は spec.md と一致させてください。

## 3. 引っ掛け値は書かない

`acceptance.spec.ts` に引っ掛け値の一覧はありません。すべて seed から機械生成します。
理由は 過去の判断 第4節のとおり2つです。

1. 人が書くと、書ける範囲しか試せない
2. **一覧を人が持つと静かに短くできる。** 生成なら短くする対象が存在しない

したがって、**このファイルに値の配列を書き足してはいけません。**
検査を強めたいときは、値を足すのではなく次のどちらかを行います。

- `HOOK_SEED` を変える（別の値の集合が出ます。同じ seed なら常に同じ値です）
- `UI_HOOK_COUNT` / `API_HOOK_COUNT` を増やす（③は1件あたりの費用が小さい）

生成器が組み立てるのは、符号位置の帯（制御文字・記号・ASCII・ラテン拡張・かな・漢字・
追加多言語面）、長さの階級（0／1／中間／境界付近／極端に長い）、数値の桁と符号と指数
（停止4領域の「金額」に対応）、値域外の年月日（同じく「日付」に対応）です。

## 4. spec.md 第4節「保護対象ルート一覧」の書式

⑤と [`scripts/check-catastrophic.sh`](../../scripts/check-catastrophic.sh) の C3 は、
**同じ書式**を読みます。spec.md 第4節の中に「保護対象ルート一覧」という文字列を含む行を置き、
その後に **1行1ルート**で列挙します。行の形は次のいずれでもかまいません。

```
- GET /admin/users
- `POST /api/orders`
| DELETE | /api/orders/:id | 他人の注文を消せないこと |
/mypage
```

- メソッドの記載が無い行は `ANY` として扱い、⑤では `GET` で叩きます。
- スラッシュの後に1文字以上が必要です。
- 「保護対象ルート一覧」の行が無い場合は、第4節全体からルートを拾います。

### 該当が無い場合は `- NONE` と宣言する

| spec.md 第4節の状態 | C3 | 終了コードへの算入 |
|---|---|---|
| ルートが1件以上ある | 各ルートを検査する | 抜けがあれば ERROR |
| `- NONE` の1行だけがある | `SKIP` を出力し、他の3種は継続する | しない |
| 一覧の見出しごと無い／項目が0行で `- NONE` も無い | `ERROR` | する |

**「認証を持つルートは無いと宣言した」なら SKIP、「何も書いていない」なら ERROR です。**
書き忘れが静かに緑になる経路は塞いだままにしつつ、認証を持たない案件（静的サイト、
社内向けの読み取り専用ツールなど）で C3 が恒久的に赤になることを避けます。
恒久的に赤になる検査は、検査そのものを外す動機を作ります。
それは 過去の判断 が名指しした「無効化の温床」であり、
検査を守るはずの設計が検査を殺します。

⑤も同じ書式を読みますが、こちらは一覧が空なら記録（`findings`）に積んで⑥で落とします。

## 5. 環境変数

| 変数 | 既定 | 用途 |
|---|---|---|
| `BASE_URL` | `http://localhost:3000` | 検査対象の URL |
| `SPEC_PATH` | `<cwd>/spec.md` | 案件の spec.md のパス |
| `HOOK_SEED` | `20260825` | 引っ掛け値の seed（整数） |
| `UI_HOOK_COUNT` | `5` | ②の件数 |
| `API_HOOK_COUNT` | `300` | ③の件数 |
| `LOGIN_ID` / `LOGIN_PW` | 空 | ①④で使う資格情報 |
| `OTHER_LOGIN_ID` / `OTHER_LOGIN_PW` | 空 | ⑤「他人として」で使う別人の資格情報 |

手元で走らせる場合:

```sh
npm i -D @playwright/test
npx playwright install --with-deps chromium
BASE_URL=http://localhost:3000 npx playwright test e2e/acceptance.spec.ts
```

## 6. CI に載せる

[`templates/ci/acceptance.yml`](../ci/acceptance.yml) を案件リポジトリの
`.github/workflows/acceptance.yml` に複写します。1つのジョブで次の順に実行します。

| 順 | ステップ名 | 内容 |
|---|---|---|
| 1 | `check-test-integrity` | 検査を弱める差分が無いか |
| 2 | `check-catastrophic` | 破滅的な脆弱性が無いか（4種） |
| 3 | `e2e` | 受入検査（①〜⑥） |

ジョブ名は `acceptance` です。ワークフロー名も `acceptance` です。

### 検査スクリプトの使い方

```sh
# BASE との差分から、検査を弱める変更を数える（既定の BASE は origin/master）
scripts/check-test-integrity.sh origin/main
scripts/check-test-integrity.sh origin/main docs/spec.md   # spec.md の位置を明示する場合

# 破滅的な脆弱性の4種を見る（第1引数は spec.md、第2引数は検査対象のルート）
scripts/check-catastrophic.sh spec.md
```

どちらも、検出ゼロなら終了コード 0、1件でも検出したら 1 を返します。

## 7. 必須検査にして自動マージを有効にする手順

> **⚠️ この節の手順は、この環境では検証できていません。**
> GitHub のリポジトリ設定であり、この作業環境からは実際に設定して確かめる手段がありません。
> 過去の判断
> も「自動マージの前提条件（branch protection の必須検査指定）を**実環境で未確認**」と
> 明記しています。**以下は未検証の手順です。** そのまま信じずに、
> 最初の1本の PR で実際に必須検査が効いているか（検査が落ちたときにマージ button が
> 押せないか）を目視で確かめてください。

必須検査として指定する名前は、`acceptance.yml` のジョブ名と同じ **`acceptance`** です。
ステップ名（`check-test-integrity` / `check-catastrophic` / `e2e`）は必須検査の名前には
なりません。GitHub が状態を報告する単位はジョブだからです。

1. リポジトリの Settings → Branches → Add branch ruleset（または Add rule）で、
   対象のブランチ（既定ブランチ）に規則を作る。
2. **Require status checks to pass before merging** を有効にし、
   検索欄に `acceptance` と入力して選ぶ。
   一度もワークフローが走っていないと候補に出ないため、先に PR を1本走らせておく。
3. **Require branches to be up to date before merging** を有効にする。
4. リポジトリの Settings → General → Pull Requests で
   **Allow auto-merge** を有効にする。
5. PR ごとに auto-merge を有効にする（`gh pr merge --auto --squash <番号>`）。
   必須検査が緑になった時点で自動的にマージされます。

補足: この構成では、AI が PR を出したあと CI の完了を待って様子を見に行く必要が
ありません。緑になれば自動的にマージされ、赤なら止まります。
